## Frontmatter

Every spec file should begin with YAML frontmatter. The frontmatter provides machine-parseable metadata that agents and tools use to index, validate, and surface documents. Keep frontmatter small and stable: prefer explicit, well-documented fields over ad-hoc keys.

Required fields

Include the following fields in every file's frontmatter. The example below demonstrates a minimal, valid header:

```yaml
type: urn:open-specs:feature
title: Short human-friendly title (<= 80 chars)
description: Single-sentence summary (<= 300 chars)
tags:
  - todo
  - ux
```

- `type`: A URI that identifies the document kind and its semantics. See [File Types](#file-types).
- `title`: A concise human display name. Keep it short and descriptive (recommended <= 80 characters).
- `description`: A single-sentence summary that explains the document purpose (recommended <= 300 characters).
- `tags`: A YAML sequence of short strings used for cross-cutting categorization and search.

Optional fields

Add optional fields when they provide value for discovery, review, or automation. These fields are helpful but not required:

- `generated`: Record of who created or exported the file and when (ISO 8601 date), for example `{ by: human:alice, at: 2026-08-13 }`.
- `verified`: List of verification events; should be present when file is generated by non human. e.g. `[{ by: human:bob, at: 2026-08-20 }]`.
- `stale_after`: ISO date after which the content should be considered stale.
- `status`: One of `draft`, `stable`, or `deprecated`. Omit to imply `stable`. Use `draft` for in-progress work and `deprecated` for archival documents.
- `for`: Only for `urn:open-specs:example` files. Reference the file for which the example is made.

Use a stable frontmatter schema across the repository so agents can rely on the same keys in every file.

### File types

| Type | Purpose |
| :-- | :-- |
| `urn:open-specs:doc` | Generic documentation such as guides, how-tos, background notes, and non-normative material. |
| `urn:open-specs:spec` | Formal specification describing product- or component-level contracts, requirements, and normative rules. Use for canonical, authoritative definitions. |
| `urn:open-specs:example` | Example data, fixtures, or snippets that illustrate usage of another document. Frontmatter SHOULD include a `for` field referencing the related document. |
| `urn:open-specs:feature` | Feature description covering intent, scope, UX flows, and constraints. |
| `urn:open-specs:user-story` | User story that captures a user scenario and acceptance criteria; small, testable, and focused. |
| `urn:open-specs:feature-rules` | Business rules and decision logic tied to a feature. Use for precise rule lists, invariants, and edge-case behaviour. |
| `urn:open-specs:persona` | Persona profile describing user archetypes, motivations, and typical behaviours. |
| `urn:open-specs:use-case` | Use case documenting interaction sequences, actors, components, and error handling. Include diagrams or sequence steps. |
| `urn:open-specs:adr` | Architecture Decision Record: concise rationale, alternatives considered, and chosen decision. |
| `urn:open-specs:component` | Component or service documentation describing responsibilities, interfaces, and deployment notes. |
| `urn:open-specs:api` | API documentation or specification; it should always be an annexe of `openapi.yaml` or `asyncapi.yaml`. |
| `urn:open-specs:runbook` | Operational runbooks and playbooks for incidents and routine maintenance tasks. |
| `urn:open-specs:monitoring` | Monitoring, SLOs, metrics, and dashboard definitions for operational observability. |

## Body

The body of the file is plain Markdown. Write for humans first: prefer complete sentences and structured sections over long, undocumented bullet lists. Organize content into clear sections that begin with level-2 headings (##). Keep examples and machine artifacts in dedicated subsections such as `Examples`, `Schema`, or `API` so parsers can locate them predictably.

When an example or machine-readable snippet is required, use fenced code blocks with explicit languages (`json`, `yaml`, `openapi`, etc.). Place canonical examples under an `Examples` heading and include small, focused samples rather than large dumps.

### Links and relationships

When you link from one concept to another you are asserting a relationship. Links should be deliberate and stable so agents can interpret them as edges in a concept graph. Prefer absolute targets: use repository-root–relative paths (starting with `/`, for example `/specs/features/tasks/feature.md`) or full URLs for external resources. Avoid relative paths (`../foo.md`) because they complicate indexing and automation. When available, link to the canonical file path or to a stable identifier provided in the target's frontmatter.

## Markdown rules

Follow these minimal formatting rules to keep files consistent and easier to parse:

- An empty line MUST be placed after every heading.
- Empty lines MUST surround lists (blank line before and after a list).
- Paragraphs and prose SHOULD be preferred; lists MAY be used when they improve clarity.
- A file with a title in frontmatter MUST NOT contain a level one heading.
